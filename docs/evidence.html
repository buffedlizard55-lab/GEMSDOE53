GEMSDOE29 & GEMSDOE32 Scientific Analysis

GEMSDOE29 Leakage Diagnosis: Following Kaufman et al. (KDD 2011), leakage occurs when target information is used to construct features that would be unavailable at test time. Because GEMSDOE29 calculated distance from the target catalogue itself, all positives had distance 0.0, collapsing learning into a trivial threshold check. Learn-predict separation requires recomputing distance features on the training set using visible faults excluding the instance's own segment, as done in H1.

GEMSDOE32 (0.2778) Analysis: GEMSDOE32 removed candidate dots within 2 pixels of mapped faults (B=2 px prune). Because test faults are by definition unmapped, dots on mapped faults are guaranteed false positives; removing them pruned FP while preserving TP. GEMSDOE53 generalizes this by pairing catalogue-flank pruning with H1 segment-exact learn-predict separation and along-strike NMS thinning.

Official Run Card (Summary; full JSON in evidence/run_card.json)

HypothesisDistance-to-known-faults features built from the training labels leak the target (a deterministic label function). Recomputing them with learn-predict separation and scoring with whole-segment hide-and-recover removes the inflation without losing the legitimate spatial signal.
MechanismFeature = log1p(min(distance to known-fault pixels, 60)). Built from the same labels it is trained on, it is exactly 0 on every positive (Exp 1: 60,988/60,988) and >= 0.6931 (distance >= 1 px) on background, so separability is 1.0.
Non-Fault Mimicking ProcessMapping bias: the catalogue traces faults that were already mapped, so proximity to a mapped trace reflects where mappers worked (survey density, road access, outcrop), not where faults are. This is a non-fault process that the holdout cannot separate from fault signal.

Limitations & Future Work

IDDescription
L-01No organizer score exists for any file from this repository. Every number is a HOLDOUT-DTI proxy with known faults as truth.
L-02The competition labels new faults that are not in the public catalogue. Our holdout rewards recovery of mapped faults only (IR-53-03).
L-03Top-ranked hypothesis H1 (segment-exact learn-predict separation) was pre-registered but NOT run. The 3-experiment and 2-hour budget was exhausted first. The submitted-candidate lane therefore does not test H1.
L-04The candidate is blocked by the 3-px overlap flag (protocol threshold 70%). The flag cannot separate copying from shared geology. The chance baseline (evidence/overlap_baseline.json) shows the overlap is placement, not just density. The protocol threshold was not changed here.
L-05Portal [0,1] rejection: the template validator (S7, scripts/validate_submission.py docstring) records a real platform rejection caused by 3,061 NaN px inside the sample's valid region. That cause is owner-documented, not independently verified. Our primary file has no NaN inside the footprint and passes the template validator. A zeros-outside fallback was rejected as non-compliant with 'outside bounds null or nan' (S1).
L-06Data was pulled from a mirror (Dropbox links in the template bridge). Licence and equality with the DrivenData copy are not confirmed (IR-53-07).
L-07The 0.2778 file is not linked to a leaderboard receipt. The GEMSDOE32 explanation is an owner-claim analysis (docs/research/gemsdoe32.md), not a verified result.

L-09Fold CIs use five folds (t, df 4). They are wide (about ±0.007 at q=0.02), so differences of ~0.001 between arms are not resolved.
L-10Protocol deviation: this lane built its own copies of the validator (now deleted, replaced by the template's scripts/validate_submission.py) and of the writer and metric (src/gems53/core.py). The shared template's src/submission_io.py and scripts/validate_submission.py are the reference. Reconciliation of core.py to the template is not finished (remaining work).
